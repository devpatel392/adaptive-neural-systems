# CLAUDE.md

Guidance for AI-assisted development in this repository. Read [docs/architecture.md](docs/architecture.md) and [docs/research-plan.md](docs/research-plan.md) before starting work.

## The person you are working with

The project owner is learning AI/ML while building this project. Treat every task as teaching as well as implementation:

- **Explain the mathematics** behind any ML code you write: what the model computes, the loss, how its gradient is derived and why the optimiser update has its form. Use equations where they help.
- **Explain architectural decisions**: the alternatives, why one was chosen and what it costs.
- Prefer clear code over clever code. A reader should be able to map code lines to equations.

## Research integrity (non-negotiable)

- **Never fabricate data, labels or results.** Do not invent benchmark numbers, write expected results into docs before running them, or hand-assign labels to make a pipeline work.
- **Router labels come from measurements.** The retrieval router is trained on targets computed by running each retrieval strategy and scoring it against ground truth. Never use hand-assigned question categories as labels.
- **Distinguish weight updates from knowledge updates.** Adding facts to a graph or index is not training. State which one happened.
- **Reproducibility:** use `adaptive_neural_systems.reproducibility.set_seed`; record config, seeds, git commit and package versions for each run.
- **Held-out evaluation:** fixed train/val/test splits; tune on validation; touch the test set only for final results.
- **Baselines first:** every new method is compared with the simple baselines listed in the research plan.
- **Report variance:** mean ± std over ≥ 3 seeds. Report negative and null results honestly.
- Do not download pretrained models or datasets without asking first and stating name, source and size.

## Hardware constraints

Intel Core i5, 16 GB RAM, integrated graphics: **CPU only**.

- Never install CUDA or GPU builds. Install PyTorch from the CPU index (`--index-url https://download.pytorch.org/whl/cpu`).
- Size experiments to train in minutes. Estimate memory before loading anything large (parameters × 4 bytes for float32, plus activations and optimiser state; Adam keeps roughly 2 extra copies of the parameters).
- Keep peak RAM well under 12 GB to leave headroom for the OS.

## Dependencies

- `pyproject.toml` is the single source of truth.
- Explain any new dependency (what it does, why it is needed, approximate size) and get approval before installing it.
- Add dependencies only in the phase that needs them; record them in the dependency table in `docs/architecture.md`.

## Coding conventions

- Python ≥ 3.11, `src` layout, package `adaptive_neural_systems`.
- Format and lint with ruff (`ruff format`, `ruff check`); line length 100.
- Type hints on public functions; docstrings that state shapes for array arguments, e.g. `x: (batch, features)`.
- NumPy randomness through `np.random.default_rng(seed)` passed explicitly, not global state.
- No hard-coded absolute paths. Data, checkpoints and run outputs live in git-ignored folders (`data/`, `runs/`, `checkpoints/`).

## Testing rules

- Every module in `src/` has tests in `tests/`.
- Test ML code mathematically: numerical gradient checks, output shapes, loss decreasing on a tiny batch (overfit test), determinism under a fixed seed.
- Keep the default test run fast (< 30 s). Mark slower tests with `@pytest.mark.slow`.
- Run `python -m pytest` and `python -m ruff check .` before declaring work done, and report actual output.

## Incremental development

- Implement only the current phase. Do not scaffold empty modules or folders for future features.
- Small, reviewable changes; one concept at a time.
- Each experiment lives in `experiments/<id>-<short-name>/` with its config, a runnable script and a results summary generated by that script.
- Update `docs/architecture.md` "Current implementation" whenever something real is added; keep plans and implementation clearly separated.

## Commit and push after every milestone (standing rule)

After every successfully completed implementation milestone, automatically:

1. Review the changed files (`git status`, `git diff`), checking for secrets, credentials, generated files and accidental modifications.
2. Run the relevant tests and quality checks: `python -m pytest`, `python -m ruff check .`, `python -m ruff format --check .`.
3. Stage only the files belonging to the milestone and commit with a descriptive message (conventional style, e.g. `feat(ml): ...`).
4. Push to `origin/main` when safe: fetch first and never force-push or overwrite remote changes.
5. Verify the remote branch contains the new commit.
6. Report the commit hash(es), files changed, check results and push status.

Do not leave completed milestones uncommitted or unpushed **unless** a test fails, a safety concern appears or a push is rejected. In those cases stop and report instead.

Git notes for this machine: the default Git TLS backend cannot verify GitHub's certificate. Use the Windows certificate store (`git -c http.sslBackend=schannel push`), which still verifies certificates. Never disable SSL verification.
